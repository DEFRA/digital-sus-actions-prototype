Measuring Software Energy Use

Insight into energy consumption can guide practitioners working on the design and development of software.

Energy use per functional unit, for example energy per API request or per user transaction helps make measurement useful for software decisions, because it connects energy consumption to the work the system actually performs. It allows software developers to compare changes to user journeys, algorithms, data movement, hosting architecture and AI approaches even when overall demand is growing.

There are a number of methods to estimate software energy consumption

  • direct measurement (tracking power used by hardware)
  • inferred from hardware activity
  • modelled from software/cloud usage

Measuring energy use directly is likely to provide the most accurate figures, whilst modelling the least.

The challenge is establishing a credible energy-per-activity figure.

As with other aspects of digital services, energy figures can also be used to:

  • Generate estimates of water and carbon emissions via conversion factors
  • Feed into estimates of the environmental impacts of the digital service or project as a whole

1.Estimating the energy of software running in the cloud

Software applications built in the cloud do not have access to power meters, sensors or usage metrics that can be directly used to measure energy use. Instead, assumptions must be used about the shared hardware it runs on and the rate at which that hardware is utilised.

For cloud software, estimate energy from the resources provisioned or consumed, for example:

instance type × runtime × estimated server power × utilisation

The Measurement page [LINK] details approaches that can be taken to converting Cloud usage metrics from supplier reporting and dashboards into energy-use estimates.

2. Measuring energy use when we have visibility of the hardware on which it runs

Software can run on equipment that is controlled by the organisation. This could be a laptop, or a server in an on-premises data centre.

  • direct measurement of hardware power
  • hardware modelling

In these cases, follow the guidance on the ‘on-prem’ Measurement page.

2. Direct measurement of software power consumption

When software runs on hardware such as server or laptops, this means there is access underlying electrical and processor interfaces to capture power consumption. Controlled experiments can be run to directly measure the power-draw of software in real time as it runs.

Approaches can involve:

  • Hardware power meters: Devices placed at the wall socket or via current clamps measure total physical power drawn by hardware such as servers and laptops
  • Power Distribution Units (PDU): In a data centre, Intelligent rack power distribution units distribute power to multiple servers, and can be used to track energy used by each.
  • Hardware power sensors: Integrated internal circuits and components that track energy consumption for processors (Core Processing and Graphical Processing Units), cores, and Dynamic Random-Access Memory (DRAM).
! Warning Direct measurement methods require that a machine’s total energy usage is apportioned between the workloads running on it at a given time.

3. Hardware utilisation models

Hardware utilisation models maps system usage metrics to energy consumption without needing physical power meters to measure it directly.

Metrics to track resource usage can include:

  • Core Processing Unit (CPU) utilisation or time
  • Graphical Processing Unit (GPU) utilisation
  • Memory use
  • Disk Input/Output (I/O)
  • Network activity
While resource utilisation and electrical power are not perfectly proportional, hardware utilisation approaches can help guide decisions on software development, testing and continuous monitoring.

There are a number of open-source software profilers and frameworks that can be used to automate hardware monitoring. Two examples are:

  • CodeCarbon: A tool that periodically samples power consumption (in Watts or kWh) from underlying hardware components
  • PowerAPI: A software-defined power meter toolkit designed to measure application-level power consumption

To convert hardware utilisation into energy use, power draw over time must be estimated.

A simple CPU model might approximate power as:

Power ≈ idle power + utilisation × (maximum power − idle power)

Software-as-a-Service and other managed software

Software is often consumed ‘as a service’, through Software-as-a-Service or Managed Software-as-a-Service models. In these circumstances the hosting and maintenance of software will be managed by the supplier and are outside of the direct control of teams working in government.

Services using a software-as-a-service, but not involved in its procurement, may still be able to get sustainability data for the software. This may be available from the supplier, or through internal measurement capability within the organisation. Where a service team has contact with the supplier, request the following metrics:

  • Energy consumption attributable to the software in kWh. For complex software comprising multiple applications, modules or functional components, energy consumption should be disaggregated at component level wherever possible.
  • Hosting location
  • Data centre Power Usage Effectiveness (if not accounted for in energy consumption)
  • Hardware embodied carbon
  • Hardware expected lifespan

These metrics can then be combined with the GHG conversion factors for electricity and an appropriate functional unit to calculate the software carbon intensity. For complex software, it may be appropriate calculate SCI scores at component level as a more granular assessment can highlight opportunities for targeted optimisation. See the section on SCI in the main measurement section for more details.

Collecting these metrics is still valuable, as although services cannot influence the hosting infrastructure, teams may be able to influence how the software is configured, used and managed. For example, services may be able to set data retention policies, storage configuration and usage configurations which impact the environmental footprint.

Estimating energy-use on the web (other proxies)

There are several approaches that have been used as proxies for energy consumption. These include:

  • ‘Time-to-Interactive (TTI)’ / Page Load Speed: Assuming faster, leaner experiences consume less device and network energy.
  • Page Weight: This approach has often used for websites by take the weight (in bytes) of web pages and multiplies this by an estimated energy-per-gigabyte factor to estimate the carbon emissions from the transfer of this data to the end user A number of online webpage carbon footprint calculators use these methods but this approach is more appropriate for simple webpages rather than complex service. See SCI for Web and the GWF article on this.

SCI for Web

What is the carbon cost of networking? It’s difficult to measure and there are competing models, but suffice it to say, two things are true.

  • The larger the size of data you are transmitting, the more energy and compute it requires to transmit. Therefore, data size is a carbon proxy. A good metric to choose here for websites is page weight – the overall size of all the assets in your website. Page weight is a carbon proxy.
  • The more distance the data has to travel, the more compute and energy is needed. Therefore, the distance that data has to travel is also a carbon proxy.

Network Data Transfer Proxies (Gigabytes Transferred): Estimates the energy cost of moving data across internal data centre fabrics or public internet routing per GB.
